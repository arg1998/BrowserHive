Vault bindings and folder policies can now be limited to specific agent harnesses. In the dashboard's binding and folder editors, a new **Harnesses** field lets you pick known harnesses (Claude Code, OpenCode, Codex, Cursor and more), **Unknown**, or a case-sensitive custom name; **All harnesses** stays the default, so existing rules are unchanged. The check runs after the principal and slug rules and only ever takes access away. Harness names are reported by the client, so this guards against mistakes, not against a client that lies: per-agent tokens remain the real boundary. An agent sees a harness refusal exactly like any other `not_authorized`; the Vault log records the real reason, `harness_not_allowed`. The database gains four nullable columns (schema v7, compatible), the REST API an optional `harnesses` field on bindings, policies and the export document, and `GET /vault/harnesses`. The vault **Tester** tab takes an optional harness and declared name and checks harness lists exactly as a fill would, naming the binding's or the folder's list when it refuses; without a harness it says which bindings have a list it did not check. The harness list recognises 16 more clients, among them Amp, Kiro, Warp, Qwen Code, Factory Droid and ChatGPT.
