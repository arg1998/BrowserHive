# Dashboard

The dashboard is the operator's view of every agent: what they are doing, what they visited, what they filled from the vault, and what they need from you. Turn it on with `--admin`. It is served on the same host and port as MCP, at `http://127.0.0.1:9876/`.

`--admin` requires `--transport http`.

## Signing in

On the first start with `--admin`, BrowserHive generates a 24-character password, prints it once in the startup banner, and writes it to `<data-dir>/admin/credentials.txt` (mode `0600`). Sign in with it; you must choose a new password (12 to 256 characters) before anything else is reachable. The seed file is then overwritten and deleted.

Lost the password? Stop the server and run `browserhive admin reset-password`.

A dashboard session expires after 15 minutes of inactivity or 8 hours in total. Watching a live view counts as activity. When it expires the dashboard sends you back to the login page.

## Layout and keyboard

A sidebar lists the pages (collapsed to icons on medium screens, a drawer on phones). The header shows connection health and notifications. The connection pill reads **Live** while the realtime connection is up, **Degraded** when a request could not reach a working BrowserHive (a network error, a timeout or a server error), and **Offline** when the realtime connection is down. A page left idle stays Live. Its popover shows the realtime state, REST, when BrowserHive last answered, and the version.

| Key | Action |
|---|---|
| ⌘K / Ctrl+K | Command palette: pages, sessions, actions |
| ⌘B / Ctrl+B | Toggle the sidebar |
| `/` | Focus the page's filter |
| `?` | Keyboard shortcuts |
| Esc | Close the topmost overlay |
| `j` / `k`, Enter | Move through and open table rows |

Theme follows the system, or pick light or dark. Filters, sorting and pagination live in the URL, so any view can be bookmarked or shared.

## Overview

Fleet health over 24 h, 3 d, 7 d, 14 d or 30 d: live sessions, sessions and tool calls in the window (with sparklines), open attention requests, errors with the error rate, active live views, and blocked URLs. The activity chart shows calls per bucket with errors stacked; click a bar to open the sessions of that time slice. Below it, a live feed of websites visited, the most frequent recent failures, and **Harnesses**: sessions and tool calls per agent in the window, with Unknown always listed; click one to see its sessions.

## Sessions

Every session, live and finished. Filter by state (live, closed, archived), owner, channel, persistence mode and harness (the agent that launched the session, see [Harness identity](mcp-clients.md#harness-identity)); search by slug or id; sort by any column. Columns show the last URL, calls and errors, blocked attempts, the agent (harness, with the workspace or model when declared), the lease countdown and the state (including "needs attention" and "being watched"). Sessions launched from a [template](#templates) show the template's name on their line, and a **Template** chip filters by template. Select rows to archive, unarchive or delete in bulk. Deleting names exactly what is erased: events, trace, screenshots, profile and downloads, terminating live sessions first.

## Session detail

The header shows the session id, state and actions: terminate, open the trace viewer, download `trace.zip`, archive, delete. When the agent is waiting on you, a banner shows the attention request or pending vault confirmations. A side rail lists owner, channel, headless or headed, persistence, current URL, lease and identity. The **Client** panel shows the harness and how it was recognised, the declared model ("not reported" when none), the workspace, the client's name, version and protocol, and any extra labels it sent. The **Session** panel shows the browser with its real version and whether it ran inside Chromium's sandbox. Both are recorded when the browser launches, so a closed session still shows them. A session from before this was recorded (BrowserHive 0.1.x) shows **not recorded**, which does not mean the sandbox was off; a session whose browser never started shows **not launched**.

Tabs:

A session launched from a template carries a **Template** badge that opens the template, and **Sign-ins protected** while agents cannot read its cookie values, run page scripts or save the sign-in ([Sealing](templates.md#sealing)); BrowserHive's own sign-in and upkeep sessions read **BrowserHive (system)**. Template sessions are never traced, which the Files tab says, and their identity is the template's.

- **Live.** The screencast of the agent's browser. Controls: start/stop, stream size (fit, 720p, 1080p, native; per viewer), **Resize agent browser** (changes the agent's real viewport), fullscreen. While an attention request is open for this session you can take over: mouse, wheel, keyboard and touch input go to the page. Outside that window input is refused. The live view of a template re-login that signs in through the live view (see below) also takes input while that re-login is open, without an attention request; the toolbar reads **Sign-in open**. During a takeover of a template session, **Page origin** shows the real origin of the page above the stream, and a warning appears when it is not on one of the template's sites (an agent can open a look-alike sign-in page and ask for attention, so do not type a password there unless you know why it is open) or when the page is not encrypted (`http:`). While the template's sites load, or when your account cannot read the template, it says it can't check the origin instead. See [Human takeover](attention.md).
- **Timeline.** Every tool call with parameters, result, duration, error code and screenshot, plus navigations, vault access, blocked URLs and attention requests. Filter by kind, follow live, expand rows. Arguments larger than 64 KiB were shortened when recorded: the row gives their full size and shows their start as text. When [telemetry](telemetry.md) is on, each call shows its `trace_id` and, with `--otelTraceUrlTemplate`, a link into your tracing backend.
- **Vault.** This session's vault access log and pending confirmations.
- **Identity.** What the browser presents to websites: user agent, client-hint brands, platform, Chrome version, locale, timezone, screen and viewport, and whether fingerprinting and humanized input are on. See [Stealth](stealth.md).
- **Files.** Data directory path, `trace.zip` with size, download, and **Open trace viewer** (Playwright Trace Viewer with actions, DOM snapshots and network, served by BrowserHive; pages' console messages and uncaught errors are not recorded, because the browser driver never enables the console and runtime domains), screenshots, downloads, and the command to open the trace locally.

## Templates

A [session template](templates.md) is a browser you sign in to once; agents then launch sessions from it already signed in. The page lists every template: its display name and the name agents use, its sites with a mark per site (**Signed in**, **Signed out**, **Check needed**, **Couldn't tell**, **Not checked**), its **Browser** (stopped, starting, running, restarting, crashed, failed) with the pages agents have open, live sessions against its cap, and when an agent last used it. Filter by status and browser state, or search by name. A template you have not finished signing in to reads **Setting up** and offers **Continue sign-in**. Each row's menu opens it, starts a **Re-login…** for one of its sites, restarts its browser, disables or enables it, and deletes it. The sidebar badge on **Templates** counts the sites that need a sign-in.

**New template** opens a five-step wizard. The step is in the URL, so a reload keeps your place. What you enter is kept in this browser tab only: closing the tab, signing out or **Cancel** forgets it, and **New template** always starts on the first step. **Cancel** is on every step; when you have entered anything it asks before discarding it.

1. **Name.** A display name, the name agents pass to `launch_session` (2 to 32 characters: lowercase letters, digits and dashes, starting with a letter) and a description agents see in `list_templates`.
2. **Sites.** The domains to sign in to, up to 16. **Sites BrowserHive knows** lists the [site packs](site-packs.md) as cards (title, domains, **Sign in by hand only** where the site refuses automated sign-ins, the default write policy, what the site's terms say, and the version adding it approves with its provenance and short SHA-256); search them and press a card to add the site; press an added card (it shows **Added**, and **Remove** when you point at it) to take the site out again. **Add a site** takes any domain too; BrowserHive keeps its registrable domain (`www.linkedin.com` becomes `linkedin.com`). When a typed domain belongs to a pack, the field says which version adding it approves. Creating the template approves exactly the pack versions shown; any other site is a generic site.
3. **Identity and network.** Browser channel, stealth level (**Standard** or **Max**: templates always run with stealth on), fingerprint, headless (with a warning: sites challenge headless browsers more often), a proxy (server, user name and the **name** of the environment variable holding the password), locale and time zone. They are fixed once the template exists; see [Identity](templates.md#identity). With a proxy, locale and time zone are required.
4. **Access.** Who may launch it (every agent, or listed principals), which harnesses (the same picker as vault bindings), the concurrent session cap, and the protections: sign-ins are protected by default, and each **Allow …** switch asks for confirmation. See [Sealing](templates.md#sealing). **Create and sign in** creates the template; on step 3, **Skip to sign-in** keeps the defaults of steps 3 and 4.
5. **Sign in.** **Open the sign-in window** opens the sign-in window **on the machine running BrowserHive**, one tab per site. When the dashboard reaches BrowserHive at an address that is not this device, a notice says where the window opens and how to reach a server without a screen ([Signing in on Xvfb](templates.md#signing-in-on-xvfb-vnc)); **Watch the window** shows its live view beside the sites, read only, so you can follow progress from here. Sign in to each site in its tab. Each site says what it waits for: a site with a [site pack](site-packs.md) reads **Signed in: BrowserHive found its sign-in** by itself once its sign-in cookies appear; any other site reads **Not confirmed yet** until you press **I'm signed in** beside it ([how BrowserHive knows](templates.md#how-browserhive-knows-you-signed-in)). **Finish** lists any [unlisted sign-ins](templates.md#unlisted-sign-ins) ("Also signed in to: … — agents can use this") with **Remove sign-in** preselected, then sets the template ready. When a site is not signed in yet, Finish says what is missing (a site you have not confirmed, or a pack site whose sign-in BrowserHive has not found; it checks once more as you finish), warns that agents will get signed-out pages there and offers to keep signing in; a site you did not confirm is kept and marked signed out, the ready screen offers **Sign in again**, which reopens the window for it, and the template page **Re-login…**. **Cancel and close the window** (or **Finish later** before it opens) leaves the template setting up. **Cancel setup** deletes the template you just created, with its browser profile and any sign-ins made in its window, after asking; it does not sign you out at the sites. When the window cannot open, the step says why and what to do: no display on the BrowserHive machine (the command to run there, or Xvfb), an unreachable proxy (change it on the template's Settings tab), too many browsers open (close a session or raise `maxSessions`), the browser not installed (the install command), or the browser closed during sign-in (open it again).

The template page shows the status, the **Browser** with **Start**, **Stop** and **Restart**, the **Re-login** menu (one item per site, with its sign-in state), **Show window** while a sign-in window is waiting or open, **Disable**/**Enable** and **Delete**. Banners warn about sites that are not signed in (**Re-login…**, not offered while a re-login is already under way), a changed browser version (identity drift), a browser running without Chromium's sandbox, saved passwords or autofill data found in its profile (**Clear saved passwords and autofill**), and unlisted sign-ins (**Remove sign-in**).

**Re-login…** asks which site (when the template has several) and how: **In a window** opens a window at the site **on the machine running BrowserHive** (the dialog names it; when the dashboard reaches BrowserHive at an address that is not this device, a notice says the window opens there, not on this device), or **With the vault** fills the site's linked vault binding in the background. When the template's browser cannot show a window (a headless template whose browser is already running, or no display on the BrowserHive machine), the re-login signs in **through the live view** instead: the dialog and the site's card say "This template's browser has no window to show here: sign in through the live view. Agents wait only while you type." and offer **Sign in in the live view**, which opens the sign-in page's live view with input on (it needs `templates:login`). A stopped headless template starts with a window for its re-login when the machine has a display. While a sign-in window is open the template's agents wait: each launch and tool call waits up to 15 s, then gets a retryable error, until the window closes. Through the live view they wait only from your first input until 2 minutes without input. Meanwhile the page shows **Agents are paused while you sign in to …** with **Let agents continue…**, which asks first (agents may change cookies while you sign in); tick **Let agents continue while I sign in** in the dialog to skip the pause. A re-login started from a notification's button waits for you (the card says who asked, for example "Asked for from Telegram (user 1180442)"): **Show window** opens it on the BrowserHive machine, or goes to the live view when it signs in there. When a refused action has a reason (another re-login is waiting, no new cookies yet), the message says it. See [Signing in again](templates.md#signing-in-again). Tabs:

- **Sites.** One card per site: a **Device-bound** badge when the site binds its sign-in to this device (the template cannot move to another machine), its sign-in state with the reason and when it was last checked (kept current as checks finish), the sign-in cookie names BrowserHive learned, whether the site is offered to agents, **Automatic re-login**, its site pack (title, version and source, **Local file overrides** when a local file is in force, **Sign in by hand only**, what the site's terms say with the clause quoted and its address as text, the **Writes** policy, where **Pack default: Confirm** follows the pack, and the counts of guards, guarded controls and security checks, linking to the pack), **Re-login…**, **Check now** and **Remove site…**. A generic site whose domain now has a pack offers **Use the … site pack…**, which names the version and SHA-256 it approves. A site a security check stopped (a suspended account, a refused sign-in) reads **Stopped: agents can't use this site** until you press **Clear stop**. **Check all now** checks every site at once; while any check runs, every Check now and Check all now reads **Checking…**. A check that finds a site signed out warns instead of reporting success. After three checks in a row that could not tell, the card warns "BrowserHive couldn't tell whether … is signed in". A re-login in progress shows on its site's card: **Waiting for you** (queued, with **Show window**), **Window open** (when it closes by itself, **I'm signed in**, **Show window**, **Cancel re-login**; **Sign in in the live view** instead of Show window when it signs in there), **Filling from the vault**, **Signed in again** (the version it saved, and **Remove sign-in** for sign-ins to other sites it found), or why it failed with **Try again…**. When the site's sign-in cookies were already there as the re-login started, BrowserHive cannot tell when you are done, so the re-login never finishes by itself: sign in again if needed, then press **Done**. **Automatic re-login** links a vault binding (**Set up…** or **Change…**): pick the binding; for a site without a site pack, give the **Sign-in page path** and the CSS selectors of the **Username field**, **Password field** and, optionally, the **Submit button**; then turn on **Re-login automatically** (off until a binding is linked). When the binding would refuse the template's fill, the editor says why; **Allow this template…** adds `template:<id>` to the binding's principals, nothing else, and asks first: BrowserHive then fills the credential only into the template's own sign-in sessions, never into agents' sessions; remove the principal on the Vault page to take it back. The binding's session names don't apply to those sign-in sessions. A binding open to every principal must list its principals on the [Vault](#vault) page first. Linking needs `templates:login` and `vault:write`; without a vault the row reads **Not enabled**. See [With the vault](templates.md#with-the-vault).
- **Sessions.** Live and recent sessions launched from the template, BrowserHive's own sessions marked **BrowserHive (system)**, **Other windows** (tabs and windows nobody's session owns, such as one you opened by hand) with **Close**, and windows that show pages of several sessions.
- **Versions.** The rolling checkpoint and the saved versions with their reason (**Re-login** for one a re-login saved), size, sign-ins per domain and health, **Last good**, **Pin**, **Restore…** (close the live sessions now or wait for them), **Save version now** and **Seed from file…** (a Playwright storage-state JSON, at most 16 MiB). A running restore or seed shows its progress; agents wait meanwhile. When one is refused (another operation running, a version saved with a key this server does not hold) the dialog says why.
- **Access.** Who may launch it, the harnesses, the cap, the **Allow …** switches with whom they apply to, and a tester that answers whether a principal and harness may use the template.
- **Settings.** The pinned identity (read only), what the browser reported at its first start, the proxy and channel (changing either restarts the browser and may sign you out, so it asks first), headless, agent windows, **Deny clipboard writes** ([what it does](templates.md#deny-clipboard-writes); off by default, applies at once; when pages that were already open need a browser restart for full effect, the panel says so and offers **Restart browser**) and the data directory.
- **Activity.** Every sign-in check, newest first: the site, what it found and why, why it ran (**Scheduled**, **Before a launch**, **Sign-in**, **Re-login**, **Check now**, **Browser started**, **After a takeover**, **Restore or seed**), how long it took and the page it ended on. Filter by site, outcome and reason; the filters are in the URL. New checks appear as they finish.

Deleting asks you to type the template's name and lists the live sessions it closes; it does not sign you out at the sites. Stopping or restarting the browser and clearing saved passwords list the sessions they close too. Disabling, restoring a version, seeding over a ready template, removing a site, each **Allow …** switch, and access changes that close sessions all ask first and name the sessions they close.

## Site packs

Listed under Templates. A [site pack](site-packs.md) is data about one site: how it signs in, how to tell the sign-in still holds, which requests and controls sign you out or change the account, which pages are security checks, and what its terms say about automation. Nothing in a pack applies until you approve it. The sidebar badge on **Site packs** counts the updates and local files waiting for your review.

The header shows when packs were last loaded, **Import…** (one pack file, at most 1 MiB; when the file is refused, every invalid field is listed) and **Reload local packs** (reads the local folder again).

**Updates available** lists, one card each, the newer versions a BrowserHive release bundles for packs you follow, and the local files that need approval. An update shows the pack, the versions from and to, where it came from, and every changed field with its old and new value as text (changes are not classified yet). **Apply…** asks first, then every template using the pack follows the new version, and the previous one is kept for **Revert**. **Reject** dismisses that version; **Pin vN** keeps the current one. A local file shows its path, its state and the difference between the approved content and the file now; **Approve…** names the file and the full SHA-256 of the content you reviewed. Later edits to the file change nothing until you approve them again.

Tabs:

- **Packs.** Filter by **Local** and **Bundled** source, by **Updates available**, or search by name or domain; the filters are in the URL. Each pack shows its title and domains, its provenance ("Bundled with BrowserHive 0.3.0", "Local file …/linkedin.com.json"), the approved version with its short SHA-256 (copy the full one), who approved it and when, the local file's state (**Approved**, **Changed since approval — review**, **Not yet approved**), how many templates use it, **Follow updates** (**Auto** follows while a template uses the pack, **On**, **Off**), **Enabled**, and why a version was skipped. Each row's menu has the same settings and **Revert…** when a previous version exists. Under 768 px the table becomes cards. **Where packs come from** shows the bundled packs, the local folder (`sitePacksDir`) with its file counts, the last load and every skipped version with its reason; updates from browserhive.ai arrive with a later release.
- **History.** Every approval, applied update, rejection and revert, newest first.
- **Guard hits.** Every request or control a pack blocked, asked you about or flagged: the guard, the method and address as text, the session and the tool. Filter by what happened.

A pack's page shows every section as text: the sign-in page in full, the signed-in check, writes and the site's terms (the clause verbatim, with the date it was checked and its address as text, never a link), the guards with their methods and resource types, guarded controls, security checks, sessions and pacing (official limits or vendor guidance, with their sources), what the site expects of the browser, the strategies with their parameters (applied from a later release), the verified dates and the sources. Beside them: the version in force with its provenance and SHA-256 (or what adding one of its sites would approve), the local file, **Follow updates**, **Enabled**, **Revert…**, **Unpin** and every version BrowserHive knows; above them the updates waiting for review, and below, the pack's history.

With `sitePacks` set to `false` the page says so and every template site is a generic site: BrowserHive learns its sign-in cookies when you press **I'm signed in**.

## Attention

The human-in-the-loop queue. Each pending request shows the agent's reason, the mode (takeover or notify), how long the agent has waited, any options it attached, and a message box. **Resolve** or **Reject** sends your message back to the agent; **Open live & take over** jumps to the live view. Requests a site pack raises are labelled: **Site check** (a page only a person can clear; take over, clear it, then **Resolve**) and **Write approval** (a request the site's write policy holds, with the site, the guard and its kind, the method and address as text, and the tool; **Approve** lets it through, **Deny** drops it). Sign-out, account, credential and destructive requests can only be decided here, not from a notification. Below the queue, the history of settled requests with outcome, wait time and who resolved them.

## Websites

Every URL any agent visited, with the most visited domains, category tags for non-public destinations (IP addresses, local hosts, FTP), and filters by session, domain and time window.

## Blocklist

The loaded rules and how often each one fired, lines in the file that do nothing (duplicates, refused patterns), attempts by source (tool boundary or network), sessions affected and top domains. **Reload blocklist** re-reads the file without a restart. When no blocklist is configured the page explains how to add one.

## Vault

Available with `--vault bitwarden`.

- **Status and unlock:** lock state, unlock by pasting a session token from `bw unlock --raw` (the dashboard never asks for your master password), sync.
- **Confirmations:** fills waiting for your approval, with the requesting session, target URL and tool. Approve, or deny with a reason recorded in the audit log only.
- **Origin tester:** type a URL, and optionally the harness to test as, and see which entries would fill there and why.
- **Folders:** each vault folder has a policy (manual, allow all, reject all), folder-wide flags and the harnesses that may use it.
- **Bindings:** per entry, the allowed origins, authorized sessions, flags and harnesses. See [Harness restrictions](vault.md#harness-restrictions).

Details in the [vault guide](vault.md).

## Vault log

The audit trail of every `vault_fill` and denied listing: time, entry, result, origin check, whether `evaluate` was enabled, session and page URL. Filterable. It never contains secrets.

## Logs

A live tail of the server log with level, module, session and trace filters, pause-on-scroll, and NDJSON export. Change the log level at runtime from the System page.

## System

Version, transport, uptime, bind address, live sessions and the browsers open against the cap (a template's browser counts once however many sessions use it), open attention requests, live views, dashboard connections, default persistence, whether `evaluate` is allowed, vault backend, blocklist, retention, database size and schema version, telemetry endpoint and data directory. A stealth section shows the stealth level, driver, fingerprint and humanize defaults and CAPTCHA mode. **Browsers and sandbox** lists the browsers found on the machine (the bundled Chromium, an installed Google Chrome or Microsoft Edge) with version and path, marks the default one, and shows for each whether it runs inside Chromium's sandbox, with Chrome's own reason when it cannot. **Template browsers** lists the templates whose browser is running, with its state, pages, memory and sessions; select one to open the template. **MCP connections** lists the agents connected over MCP, live ones first, then recent ones; select one to see how its harness was recognised, its model and workspace, client and protocol, User-Agent, IP, any conflicting signals and extra labels. **Public address** shows `publicUrl` and whether it reaches this BrowserHive (see [public address](notifications.md#public-address)), with **Check again**. A session's Details tab shows its browser version and whether that session ran sandboxed, for live and closed sessions alike. Banners warn when `evaluate` is enabled together with the vault, when disk space is low, or when a subsystem is degraded. The configuration table lists every effective setting with its source (`cli`, `file`, `env`, `default`, `derived`) and the values it shadowed; secrets are shown as redacted. A value the config file reads from an environment variable has a `$NAME` chip under its source (outlined when the variable was not set and the default is used); select it to see the value as written in the file, or, for a secret, just the variable. **Only values from references** narrows the table to those keys, and the filter also matches variable names. See [References](configuration.md#references).

## Notifications

Persisted notifications for attention requests, tool errors, crashed sessions and pending vault confirmations, grouped by day. Mark as read or dismiss, individually or all at once. Once an attention request or vault confirmation is settled (in the dashboard, by a timeout, or elsewhere), its row keeps its place and shows the outcome as a small pill (**resolved**, **expired**, or **closed** when the agent stopped waiting), and a toast still on screen for it closes. See [Notifications](notifications.md).

**Channels** (Notifications → Channels) sends notifications to your phone through Telegram, Discord (webhook or bot), ntfy or a webhook: one card per channel with its status, last delivery, 24-hour counts and, when act buttons are on, whether answers from the chat reach BrowserHive; and an **Add channel** wizard with a live preview and a test message. Its **What to send** step switches **Answer from the chat** on and edits who may answer, and its **Reports** section sets a daily or weekly digest, the channel's time zone and the anomaly alerts; a card shows the next digest and **Send now** (a preview of the real digest, then a send on demand). The delivery log marks a digest sent after downtime as **late**. **Delivery log** lists every send, edit and delete, and says why anything was not sent. **Actions** lists every press of an act button: who, which button, from which chat, and what happened. **Reports** keeps every digest and anomaly alert once per period (the inbox's **Reports** chip shows the same), opens each as a page with its facts, chart and tables, and has **Reports in BrowserHive**: a digest and anomaly alerts for the dashboard itself, with no channel needed. See [Channels](notifications.md#channels), [Answer from your phone](notifications.md#answer-from-your-phone) and [Reports in BrowserHive](notifications.md#reports-in-browserhive).
